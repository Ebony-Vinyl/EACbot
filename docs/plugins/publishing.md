# 社区插件开发与发布流程

状态：v1。公开仓库 [Ebony-Vinyl/eacbot-extensions](https://github.com/Ebony-Vinyl/eacbot-extensions) 已创建，包含模板、JSON Schema、验证脚本和签名发布工作流；签名私钥只在受保护 Actions Secret 与本机安全目录。用户可提交 PR 收录新功能和版本，维护者审核后由工作流签名发布。

## 1. 仓库职责

EACbot 主仓库维护宿主、SDK、testkit、schema 与默认一方插件适配。独立扩展仓库维护目录元数据、社区插件源码/明确源码引用、模板、发布与撤回记录。不长期维护两份 Muse 或其他插件实现。

建议结构：

```text
eacbot-extensions/
  plugins/<publisher>/<name>/
    eac-plugin.json
    README.md
    LICENSE
    NOTICE
    CHANGELOG.md
    config.schema.json
    src/
    tests/
    screenshots/
  templates/
  schemas/
  catalog/
  .github/workflows/
  .github/CODEOWNERS
  CONTRIBUTING.md
  SECURITY.md
```

此目录树是待创建仓库规范，不是本仓库当前文件列表。二进制制品放受管理 release 存储，目录只引用不可变摘要；图标/截图包含作者权利与来源，不允许真实用户信息。

## 2. 开发步骤

1. 选择 SDK 版本与已有服务合同，优先新增插件而非修改 Agent loop。
2. 从最小模板建立 manifest、config schema 和中英文说明，声明实际权限/依赖；纯主题不启动后端。
3. 在独立 fixture 中安装开发包，以假服务、临时时钟、假账户测试工具与 UI。
4. 先写合同失败用例，再实现；必须测试撤销、取消、幂等、故障和停用。
5. 在目标 OS/arch 构建制品，锁依赖并生成 SBOM、文件摘要和许可证清单。
6. 开发者验证从空安装到卸载，不使用本机已存在但 manifest 未申报的 Python/.NET/Node 工具蒙混通过。
7. 提交 PR，附功能演示、范围、验收记录、权限理由、已知限制与迁移说明。

SDK 和脚手架尚未发行，因此不提供不存在的安装命令。实施 M1 时将实际脚本、版本与示例加入模板；能够从干净 fixture 复现后才写进使用说明。

## 3. PR 必填内容

- pluginId、发布者可验证身份、源码 revision、许可证及文件级例外。
- 解决的用户需求，与已有插件差异；禁止只换名重复发布。
- manifest、权限申请理由、数据去向/留存、隔离要求与依赖。
- 支持平台矩阵：通过、失败、未验证分别列出。
- 测试命令/输出、假服务 fixture、必要的真实授权测试证据；注明哪些需要账号。
- UI 截图和动效录屏；空、错、离线、无权限状态。
- 升级与回滚策略、配置/状态迁移、停用清理、受影响旧版本。
- 外部 API/条款/许可证依据；无许可证或冲突声明不能被“开源”二字掩盖。

新发布者及权限增加需人工安全复核；扫描结果不是人工审核替代品。官方/已审核标记仅由渠道维护者设置。

## 4. CI 信任分区

### 外部 PR 检查

只读 token、无发布密钥、独立低权限 runner；不得使用带秘密的 pull_request_target 执行 PR 代码。锁定 action 版本/摘要，限制网络出口、运行时间、磁盘和资源。恶意包检查脚本从受信目录执行，下载内容不作为解释器 CWD。

检查：schema、路径/包结构、依赖锁、许可证/NOTICE、secret 扫描、SBOM/漏洞、危险 API 与越权依赖、工具权限差异、testkit、安装/卸载/回滚、UI 合同、目标平台构建。

### 合并后发行

受保护分支与环境审批；确认被审核的 revision；在干净环境可追踪构建；签名工作只签已校验制品摘要，不运行来自包的任意脚本。签名密钥不进入插件 runner。优先短期凭据或硬件/托管签名，保护密钥轮换和恢复流程。

发布制品 → 校验公开地址摘要 → 更新签名索引/sequence → 用独立干净客户端做安装 smoke → 宣布发行。发布目录不能指向 latest、浮动 branch 或可变标签而无精确摘要。

## 5. 版本与事故响应

SemVer 表示插件合同/功能变化；SDK API、宿主最低版本和数据 stateVersion 分别标记。新增权限是显式安全变化，不因 patch 版本而忽略。

漏洞处理：私密报告 → 维护者评估 → 必要时签发撤回 → 修复版本与迁移 → 验证 → 恢复发布。撤回说明影响范围与用户恢复动作，不自动删除用户数据。

维护者失联、上游 API 关闭或许可证不明确时标记维护状态，停止新增自动更新；不能让市场继续显示“正常可用”。

## 6. Muse 的专项执行要求

插件标准就绪后，按用户要求给实现智能体明确任务：直接复用、改造 KugouMusic.NET，开发登录/音乐能力和六层 Bot 联动，不另选后端。另一验收智能体独立跑场景，不能以 UI 演示或工具已注册代替真实播放。

此分工用于后续功能实施；当前文档由主执行者编写。上游文件保留署名、许可证和 revision 记录；有不一致使用声明时先确认适用许可，再决定复制范围。

## 7. 发布完成定义

一个陌生开发者可以按模板制作插件，一个空白 EAC fixture 可以从签名测试源安装、启用、被 Bot 调用、停用与卸载；升级失败可按文档恢复。真实平台限制明确显示，截图、日志、源代码与发行制品相互对应。

验收表见[发布验收](../verification/plugin-release.md)，安全检查见[审核规范](security-review.md)。
